# Create a New Targets Pipeline for LPC

``` r

library(levinmisc)
```

## Introduction

The `targets` package is a tool for developing reproducible research
workflows in R. Details of the package motivation and tools are
described in detail: <https://books.ropensci.org/targets/> and
<https://docs.ropensci.org/targets/>.

### Example Workflow

1.  Create a new R project

2.  Run the
    [`levinmisc::populate_targets_proj()`](https://mglev1n.github.io/levinmisc/reference/populate_targets_proj.md)
    function in the R console - this function is described below in
    detail, and will initialize your project with helpful files/folders
    to start building your `targets` pipeline.

3.  Keep input data in `Data/` and write pipeline outputs to `Results/`.
    Both directories, the `targets` data store, and logs are excluded
    from git, and a pre-commit hook blocks commits that would add data
    or participant identifiers. If the project was not yet a git
    repository, run `git init` and then
    `git config core.hooksPath .githooks`; a fresh clone of the project
    needs the second command once.

4.  Open the project directory itself in code-server (File \> Open
    Folder) and trust the workspace when prompted, so the editor tasks
    in `.vscode/tasks.json` load.

5.  Modify the `Pipelines.qmd` file to specify your analyses. The
    `targets` documentation can be useful for specifics.

6.  Knit/Render `Pipelines.qmd` to convert your markdown document into a
    series of R scripts that will actually run your analyses.

7.  Run the pipeline. The `Pull, render, and run pipeline` editor task
    pulls the latest code from GitHub, renders the pipeline file, and
    runs `targets::tar_make()` in its own terminal, leaving your R
    terminal free. When the run finishes or fails, it can send a Slack
    or ntfy notification (see below). The run happens inside the
    code-server job, so request a session long enough for the whole
    pipeline.

8.  Modify `Results.qmd` to present the results of your analyses.
    Rendering this file allows you to mix text describing your
    analyses/methods and include citations alongside the actual results
    of your pipeline. The `targets::tar_read()` function should be used
    heavily to load pre-computed results from your pipeline.

## populate_targets_proj()

The `populate_targets_proj` function can be run within a new project
folder to initialize the project with the files/folders necessary for
deploying a `targets` pipeline on the LPC at Penn. This includes
creating a `Pipelines.qmd` file containing boilerplate for running
analyses, a `Results.qmd` file which can be used to visualize the
results, editor tasks, a pipeline run script with notifications, and git
safeguards against committing data or participant identifiers.

The `runtime` argument chooses the R installation the pipeline runs
against. `"native"` (the default) loads the LPC’s R module
(`module load R/4.5`) and leaves the package library to `renv`.
`"container"` instead runs the main `targets` process and every LSF
worker inside the LPC’s RStudio Singularity image, reading packages from
a library built against that image’s R, which is the right choice only
for a project whose library was built against that image. Mixing the two
fails at run time: a worker that loads a library built for a different R
version reports errors such as `unused arguments (controller = ...)`,
because the worker and the controller end up running different `crew`
versions.

The `"container"` runtime is still supported but will lose support in a
future release, because the lab no longer runs R through Singularity.
New projects should use the default `"native"` runtime. The editor tasks
always use the native R module, whichever runtime is chosen.

``` r

#' \dontrun{
populate_targets_proj("test")
populate_targets_proj("test", runtime = "container")
#' }
```

The
[`populate_targets_proj()`](https://mglev1n.github.io/levinmisc/reference/populate_targets_proj.md)
function creates several files/folders within the project directory:

- `Pipeline.qmd` - Quarto markdown file which can be used to create a
  Target Markdown document that specifies a `targets` pipeline for your
  analyses. See:
  <https://books.ropensci.org/targets/literate-programming.html#target-markdown>
  for details. Remember to knit/render this document in order to
  generate the pipeline.

- `Results.qmd` - Quarto markdown file which can be used to display the
  results generated by the `targets` pipeline specified in
  `Pipeline.qmd`. It renders a self-contained HTML report, which can be
  committed once the pre-commit hook has checked it.

- `build_logs/` - Directory where `crew` LSF worker logs are stored

- `Data/` and `Results/` - Directories for input data and pipeline
  outputs; their names are set by the `data_dir` and `results_dir`
  arguments. Both are excluded from git.

- `.run-pipeline.R` - Script the editor’s run task calls. It runs
  `targets::tar_make()`, prints a summary, sends an optional
  notification, and exits with status 1 if the pipeline failed.

- `.vscode/tasks.json` - Editor tasks to pull from GitHub, render the
  pipeline file, run the pipeline, or do all three in sequence
  (`Pull, render, and run pipeline`), plus a task to render the results
  report. Code-server loads the file only when the project directory
  itself is opened as the workspace and trusted. The comment at the top
  of the file shows keybindings to add to your user `keybindings.json`:
  one runs the combined task, one runs only the pipeline step through
  `Rscript`, and one runs `targets::tar_make()` in your R session
  through the vscode-R extension.

- `.gitignore` - Entries added for the data, results, and log
  directories, the `targets` data store (`_targets/`), scripts generated
  by rendering the pipeline file, and common data file types. Rendered
  HTML reports are not ignored. Existing entries are kept.

- `.githooks/pre-commit` - Git hook that blocks any commit staging a
  file from a protected directory, a file with a data file extension, a
  file larger than 5 MB (25 MB for HTML reports), or text shaped like a
  PMBB participant ID. Set `git_safeguards = FALSE` to skip both the
  `.gitignore` entries and the hook. Details are below.

### Participant identifier check

The pre-commit hook searches every staged text file for strings shaped
like a PMBB ID: `PMBB` followed by digits, in upper or lower case, with
an optional space, underscore, or dash. The pattern also matches
truncated IDs and IDs inside longer strings, such as `sample_PMBB…_A`.
It decodes SVG figures embedded in self-contained HTML reports and
searches their text too; text drawn inside PNG figures cannot be
checked. The hook uses ripgrep (`rg`) when it is installed and `grep`
otherwise, with identical results, and needs no configuration or
identifier list.

When it finds an identifier, the hook blocks the commit and lists each
file and line with the value masked (for example `PMBB*************`),
so its output is safe to share. Fix the source of the report, for
example by not printing an ID column, re-render, and stage the file
again. To add other identifier shapes, extend `ID_PATTERN` in
`.githooks/pre-commit` with regular-expression alternation
(`'pattern1|pattern2'`). After checking a file yourself,
`git commit --no-verify` bypasses the hook once.

### Pipeline notifications

`.run-pipeline.R` can notify you when a pipeline completes or fails. The
message contains the status, elapsed time, target counts, and the names
of errored targets. It never contains error messages or target values,
because R errors can echo data values and the message leaves the
cluster; the full error is printed in the task terminal. Notifications
are sent with the `curl` command-line tool, so no extra R packages are
needed in the project library. They are configured once per user in
`~/.Renviron`, never in the project.

**Slack.** Create an incoming webhook for the channel that should
receive messages:

1.  Go to <https://api.slack.com/apps>, choose **Create New App**, then
    **From scratch**, and pick the lab workspace.
2.  Open **Incoming Webhooks** and switch on the activation toggle.
3.  Choose **Add New Webhook to Workspace**, pick the channel, and
    select **Authorize**. If the workspace restricts apps, this becomes
    a request that a workspace admin must approve.
4.  Copy the webhook URL and add these lines to `~/.Renviron`, then
    restart R:

&nbsp;

    LEVINMISC_NOTIFY=slack
    LEVINMISC_SLACK_WEBHOOK=https://hooks.slack.com/services/...

Treat the webhook URL like a password: anyone who has it can post to the
channel. The Slack desktop and phone apps show each message as a
notification.

**ntfy.** As an alternative, ntfy (<https://ntfy.sh>) delivers push
notifications to its phone app, Mac app, or website. Subscribe to a
hard-to-guess topic, then add:

    LEVINMISC_NOTIFY=ntfy
    LEVINMISC_NTFY_URL=https://ntfy.sh/your-hard-to-guess-topic

Set `LEVINMISC_NOTIFY_START=true` to also be notified when a run starts.
With `LEVINMISC_NOTIFY` unset, the script prints its summary in the
terminal only.

### Updating an existing project

Re-run
[`populate_targets_proj()`](https://mglev1n.github.io/levinmisc/reference/populate_targets_proj.md)
in an existing project to add files introduced by newer versions of this
package, such as `.run-pipeline.R` or the editor tasks. Existing files,
including your `Pipeline.qmd` and `Results.qmd`, are kept, and the
function lists each one it kept. When `title` is not given and the
project has one `*-Pipeline.qmd` file, its name supplies the title. Pass
`overwrite = TRUE` only to replace existing files with fresh templates.

The pre-commit hook is the exception: a re-run always updates it, so
older projects gain the identifier check, and a previous version that
differs is saved as `.githooks/pre-commit.bak`. If the project’s
`.gitignore` still contains a `*.html` line from an earlier version, the
function warns; delete that line to commit rendered reports. LSF scripts
from earlier versions, such as `submit-targets.sh`, are left in place.

## Optional LSF submission scripts

Pipelines are normally run from code-server on a compute node with the
editor task above. To submit the main `targets` process as its own LSF
job instead, for example from a submission host such as `scisub7`, call
`populate_targets_proj(lsf_scripts = TRUE)`. This also writes
`submit-targets.sh` and the hidden helper `.make-targets.sh`, whose
contents follow the `runtime` argument so that the main `targets`
process runs under the same R as the workers. Run `submit-targets.sh`
from the root directory of your project once `Pipeline.qmd` has been
knit/rendered. The script accepts command line arguments:

    Usage: ./submit-targets.sh [-n NUM_WORKERS] [-j JOB_NAME] [-o OUTPUT_LOG] [-e ERROR_LOG] [-q QUEUE] [-m MEMORY] [-s SLACK] [-h HELP]

    Submit a job using the LSF scheduler with the specified number of CPUs and memory usage.

    Options:
      -n NUM_WORKERS Number of workers (cpu cores) to request for running the targets pipeline (default: 1)
      -j JOB_NAME    Name of the job (default: make_targets)
      -o OUTPUT_LOG  Path to the output log file (default: build_logs/targets_%J.out)
      -e ERROR_LOG   Path to the error log file (default: build_logs/targets_%J.err)
      -q QUEUE       Name of the queue to submit the job to (default: voltron_normal)
      -m MEMORY      Memory usage for the job in megabytes (default: 16000)
      -s SLACK       Enable slack notifications; requires setup using slackr::slack_setup() (default: false)
      -h HELP        Display this help message and exit

The `-s true` flag of `submit-targets.sh` sends start and finish
messages through the `slackr` package, which must be installed and
configured separately (<https://mrkaye97.github.io/slackr/index.html>).
It does not report failures; the webhook notifications from
`.run-pipeline.R` described above do.

### Use {crew} for parallelization

The `crew` and `crew.cluster` packages have enabled the use of
heterogenous workers
(<https://books.ropensci.org/targets/crew.html#heterogeneous-workers>),
that can be used to deploy `targets` pipelines either locally or on HPC
resources. The
[`use_crew_lsf()`](https://mglev1n.github.io/levinmisc/reference/use_crew_lsf.md)
function is designed to return a block of code to rapidly enable the use
of heterogeneous workers on the Penn LPC. By default, this function
creates workers that submit to different queues (eg. `voltron_normal`,
`voltron_long`), and allocate different resources (eg. a “normal” worker
will use 1 core and 16GB memory, while a “long” worker will use 1 core
and 10GB memory).

[`use_crew_lsf()`](https://mglev1n.github.io/levinmisc/reference/use_crew_lsf.md)
takes the same `runtime` argument as
[`populate_targets_proj()`](https://mglev1n.github.io/levinmisc/reference/populate_targets_proj.md),
which controls the shell lines that open each worker script. Under
`"container"` the worker exports `R_LIBS_USER` and `SINGULARITY_BIND`
and then runs R through `singularity exec`; under `"native"` it runs
`module load R/4.5` and nothing else, so the project library comes from
`renv/activate.R` (`crew_options_lsf()` defaults `cwd` to the project
directory). The two branches also differ in the `crew.cluster` interface
they emit: the container branch keeps the older `lsf_*` arguments to
`crew_controller_lsf()`, which is what the `crew.cluster` build inside
the image understands, while the native branch uses the
`crew_options_lsf()` interface that replaced them.

``` r

#' \dontrun{
use_crew_lsf()
use_crew_lsf(runtime = "container")
#' }
```
